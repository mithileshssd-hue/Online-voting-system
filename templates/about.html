How the System Works

A transparent look at the architecture, security guarantees, and database mechanics.

📐 System Architecture

The Online Voting System follows a modular client-server web architecture connecting a modern web frontend to an existing Python backend and local SQLite database:

Browser Client (HTML5 / CSS3 / JavaScript)
↓ HTTP / JSON API via JavaScript fetch()
Flask Web Application Layer (app.py)
↓ Direct Python Function Calls
Existing Python Logic (database.py, security.py, otp.py)
↓ Parameterized SQL & Atomic Transactions
SQLite Database (data/voting.db)
📦 Key Components & Responsibilities
Module Technology Responsibility
Frontend HTML5, CSS3, JS, Bootstrap 5 Responsive presentation, user input handling, and async API calls.
API Layer Flask (app.py) Routes requests, manages sessions, and delegates to core Python logic.
Database SQLite3 (database.py) Manages tables, transactions, voter records, and results calculation.
Security security.py Regex validation for Voter IDs and SHA-256 password hashing.
OTP System otp.py Simulated OTP generation with 120-second expiration and 3-attempt limit.
🎓 1st-Year CSE Viva Q&A Highlights

Double voting is prevented through two complementary levels:
  1. Application Level: The submit button is immediately disabled on click, and the backend verifies that has_voted == 0 before accepting the ballot.
  2. Database Level: In database.py, an atomic SQLite transaction writes to the votes table (which has a UNIQUE constraint on voter_id) and updates users.has_voted = 1. If any constraint is violated, the entire transaction is rolled back.

Passwords are never stored in plain text. When an administrator creates an account or logs in, the plain password is converted into a 64-character hexadecimal SHA-256 cryptographic hash. The database only stores this hash. Even if someone inspects the SQLite database file, they cannot reverse-engineer the original password.

In commercial software, OTPs are dispatched through SMS gateways like Twilio or email APIs. For this academic demonstration, the backend generates a random 4-digit code with full security constraints (120-second expiration and 3 attempts maximum), but displays the code in an educational simulation banner so testers and examiners can evaluate the workflow without requiring real phone numbers or external SMS subscriptions.
